1What Is This System?

The Telecom Outage Resolution BOB is a proof-of-concept agentic AI system built for telecom operations. It acts as a digital first-responder: the moment a customer or NOC operator reports a service issue in plain English, the system spins up a coordinated pipeline of seven specialised AI agents that each do exactly one job, pass their findings forward, and collectively produce a complete resolution package.

Core promise: Free-text complaint → structured ticket + root-cause analysis + resolution steps + customer message, all in under 8 seconds, with full audit trail and zero PII exposure.

Why 7 Agents?

Single-agent systems suffer from context overload and undifferentiated responsibility. By splitting the workflow into specialised agents, each unit can be tested, cached, replaced, and scaled independently:

#AgentJobSLA
1Intent RecognitionClassifies issue type, affected service, location, and priority from raw text using IBM NLU<500 ms
2Ticket ClassificationCreates a structured ticket with severity (P1–P4), queue routing, and SLA deadline<200 ms
3RCA AnalysisRetrieves similar past incidents from ChromaDB (RAG) and calls Granite LLM to synthesise root cause<2 s
4aEscalationApplies 4-rule decision tree: escalate, assign level, compose notification, estimate cost impact<500 ms
4bParallel AnalysisConcurrent customer, network, and operational impact assessment (runs alongside Escalation)<1 s
5Response GenerationProduces prioritised resolution steps and a professional customer-facing message via Granite<1.5 s
6FeedbackEstimates CSAT impact, checks SLA compliance, extracts learning points, writes final audit entry<500 ms

Agents 4a and 4b run concurrently via asyncio.gather, saving ~500 ms vs. sequential execution.

5Data Guide — Where to Find & How to Feed

5.1 Seed Data (included — synthetic, ready to use)

All data in bobCode/data/seed_data/ is fully synthetic. No real customer records, real network coordinates, or real company names are used.

FileContentsUsed by
incidents.json 10 synthetic telecom incidents (fiber cut, signal degradation, DNS failure, billing outage, power failure, capacity exhaustion, software bug, subsea cable, backhaul, core network) ChromaDB ingestion → RCA Agent RAG retrieval
knowledge_base.txt 6 sections of resolution patterns: Fiber Cut, Signal Degradation, Core Network, Capacity, Power, Escalation Thresholds + SLA targets ChromaDB ingestion → RCA Agent context chunks

5.2 Each incident record schema

{
  "id":                 "INC-2024-000001",   // synthetic sequential ID
  "type":               "fiber_cut",          // canonical issue type
  "service":            "4G_LTE",             // affected service
  "location":           "Sector-BX-North",    // synthetic location
  "description":        "...",                // full incident description
  "root_cause":         "...",                // actual root cause
  "resolution":         "...",                // how it was resolved
  "affected_customers": 47000,               // integer count
  "severity":           "P1",                // P1–P4
  "mttr_minutes":       112,                 // mean time to restore
  "prevention":         "..."                 // future prevention tip
}

5.3 Adding your own incidents

  1. Append new records to data/seed_data/incidents.json following the schema above.
  2. Use synthetic data only — fictional locations (grid references), anonymised IDs, no real customer data.
  3. Re-run ingestion: python data/ingest.py (safe to re-run — uses upsert).
  4. New incidents are immediately available to the RCA Agent via semantic similarity search.
Data compliance: Never add real customer names, real phone numbers, real email addresses, or real geographic coordinates to seed data. The system applies PII masking to inputs, but seed data that already contains PII will appear in RAG context without masking.

5.4 Adding resolution patterns to the knowledge base

Edit data/seed_data/knowledge_base.txt and add new sections following this format:

PATTERN: Your Pattern Name
Symptoms: ...comma-separated or multi-line symptoms...
Immediate Actions:
  1. First step
  2. Second step
Root Cause Indicators: ...
Resolution Time: X–Y minutes
Prevention: ...

Then re-run python data/ingest.py. The chunker splits on PATTERN: markers automatically.

6Integrating Real LLMs & IBM Services

Default is mock-first. All 418 tests and the full demo run with USE_MOCK=true — zero IBM credits consumed. Switch to live only when you have credentials and are ready.

6.1 Activating IBM watsonx.ai (Granite 13B)

Used by: RCA Agent (root cause synthesis) and Resolution Agent (customer message generation).

Lite Plan: 100 free inference calls/month. The POC budget is ≤10 calls total.

  1. Get credentials from IBM CloudGo to cloud.ibm.com → watsonx.ai → Manage → API keys. Copy the API key and Project ID.
  2. Set in .env
    WATSONX_API_KEY=your_api_key_here
WATSONX_PROJECT_ID=your_project_id_here
WATSONX_URL=https://us-south.ml.cloud.ibm.com
USE_MOCK=false
  3. Verify credentials at startupThe Settings.validate_live_credentials() method checks all required keys and logs warnings for any missing ones when USE_MOCK=false.
  4. Monitor budgetCall GET /health — check api_calls_used stays ≤10. The GraniteClient._real_call_count class-level counter tracks every live call.

Model parameters (hardcoded, budget-safe):

max_new_tokens:     256   # capped — prevents runaway generation
temperature:        0.1   # low = deterministic, factual
top_p:              0.9
repetition_penalty: 1.1

Graceful degradation: If the Granite live call fails (network error, quota exceeded), the client automatically falls back to the keyword-based mock response. The pipeline never crashes due to LLM unavailability.

6.2 Activating IBM Watson NLU

Used by: Intent Recognition Agent (entity extraction, keyword detection, sentiment).

Lite Plan: 30,000 free calls/month — effectively unlimited for this POC.

NLU_API_KEY=your_nlu_api_key_here
NLU_URL=https://api.us-south.natural-language-understanding.watson.cloud.ibm.com/instances/XXXX

Get these from IBM Cloud → Natural Language Understanding → Manage → Credentials.

NLU features activated: entities (limit 10), keywords (limit 10), sentiment (document-level). All applied to PII-masked text only.

6.3 Activating IBM Cloudant

Used by: All agents (audit trail), Feedback Agent (ticket write), Watson BOB (ticket persistence).

Lite Plan: Unlimited — no quota concern.

CLOUDANT_URL=https://ACCOUNT.cloudantnosqldb.appdomain.cloud
CLOUDANT_API_KEY=your_cloudant_api_key_here

Get these from IBM Cloud → Cloudant → Manage → Credentials → IAM API key. Collections are created automatically on first write via the SDK.

6.4 Using a different LLM (non-Granite)

The GraniteClient is the only file that references IBM watsonx.ai SDK. To swap in a different LLM:

  1. Edit bobCode/core/granite_client.py
  2. Replace the live path (lines 107–125) with your provider's SDK call (OpenAI, Anthropic, etc.)
  3. Keep the same signature: async def generate(prompt: str, ...) -> str
  4. The max_new_tokens=256 cap and fallback to mock remain unchanged

No other files need to change — all 7 agents and the orchestrator call only granite_client.generate().

9Security & Guardrails

PII Protection (applied at every data boundary)

PatternExample InputAfter Masking
Phone numberCall +1 555-012-3456Call [REDACTED]
Email addressjohn.doe@example.com[REDACTED]
US SSNSSN: 123-45-6789SSN: [REDACTED]
Credit card4111 1111 1111 1111[REDACTED]

Input validation (applied before any agent processes text)

  • Maximum 2000 characters
  • SQL injection blocked: UNION SELECT, DROP TABLE, -- comments, etc.
  • Prompt injection blocked: ignore all previous instructions, you are now a, instruction tags ([INST], <|im_start|>), etc.
  • Rejections return a generic safe message — attack patterns are never revealed

Output validation (before every AgentResponse is returned)

  • Confidence threshold: ≥ 0.5 required; below threshold → escalate to fallback
  • Required fields check: agent-specific schema validated
  • PII scan: all string fields in agent output checked for leaked PII

Audit trail

Every orchestration run writes immutable sanitised events to audit_trail (in-memory in mock mode; Cloudant in live mode). What is never logged: raw user text, unmasked PII, stack traces, credentials.

Network security

  • CORS restricted to http://localhost:5173 — never wildcard
  • Only GET and POST methods accepted
  • .env is in .gitignore — credentials never committed

For each incident submitted, the system produces:

  1. Structured ticket — ID, severity (P1–P4), routing queue, SLA deadline, category
  2. Root cause analysis — hypothesis with confidence score (0–1), evidence list from historical incidents, estimated scope (customers affected), MTTR estimate
  3. Escalation decision — escalate true/false, escalation level (None / L2 / Management / Executive), notification list, revenue impact estimate
  4. Impact analysis — customer impact (count, severity), network impact (services affected, BGP state), operational impact (crew needed, cost estimate)
  5. Resolution steps — ordered, actionable, tailored to issue type (e.g. "Activate BGP failover", "Dispatch fiber repair crew with OTDR")
  6. Customer message — professional, jargon-free, ready to send via SMS/email/portal
  7. Feedback & learning — SLA compliance check, CSAT estimate, learning points for post-mortem
  8. Audit trail entry — immutable, sanitised, timestamped — regulatory-ready

What the system does NOT do (current POC scope)

  • It does not autonomously push changes to live network equipment (human approval required)
  • It does not send actual SMS/email/push notifications (outputs the message draft only)
  • It does not store real customer data — all seed data is synthetic
  • Speech-to-text / text-to-speech interfaces are optional and not implemented in this POC
